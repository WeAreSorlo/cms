# The admin API

The admin API, under `/api/`, is what the admin itself calls, and its replies take the shapes in [the API's replies](api.md#replies). The admin uses it with the session cookie, which every route but `/api/session` and those under it needs, since they're how someone gets a session. Its entries are their drafts, with `archivedAt`, `createdBy` and `updatedBy`, `status`, which is `draft`, `published` or `changed`, `version`, the number of the newest version, or null before the first save, and `publishedVersion`, the number of the version that's live, or null. Its media also have `createdBy`.

## Bulk saves

`PATCH /api/types/:type/entries` saves the grid's edits, in the shape the user chose on 30 October 2026. Each entry's `values` holds just the fields that changed. A group's fields merge into what's saved one by one, at any depth, and any other field's value replaces what's saved, so a list or a link is sent whole. `publish: true` publishes every entry that saves, after every check, and a type without drafts publishes anyway. Pages keep their parents.

```json
{
  "publish": false,
  "entries": [
    { "id": "0192f0c4-…", "values": { "title": "Hello", "seo": { "title": "Hi" } } },
    { "id": "0192f0c5-…", "values": { "price": -1 } }
  ]
}
```

Each entry saves on its own, in the order sent, through the same code as `PUT /api/entries/:id`, so those that pass are saved whatever happens to the rest. Each is read and locked in its save's transaction, and its changes merge into what that read finds, so another save's changes to its other fields are kept, however close together the two land. The reply is always 200, with a result for each entry: its `id` and the `status` that `PUT /api/entries/:id` would have replied. That's 200 with the saved entry in `data`, 422 with the validation report in `report`, or another status with a `message`, such as 404 for an ID that isn't an entry of the type, and 409 for an archived entry or a page whose parent isn't live. When two entries take the same slug, the first saves and the second gets a 422 on its slug.

```json
{
  "data": [
    { "id": "0192f0c4-…", "status": 200, "data": { "id": "0192f0c4-…", "values": { "title": "Hello" } } },
    {
      "id": "0192f0c5-…",
      "status": 422,
      "report": {
        "isValid": false,
        "fields": { "price": { "isValid": false, "messages": ["This field requires a minimum value of 0."] } }
      }
    }
  ]
}
```

The whole request replies 400 unless it lists 1 to 100 entries as `{ id, values }`, each once, whatever its case, 404 for an unknown type, and 409 for a singleton or while a content migration hasn't run.

## Ticked entries

Select all, Archive and Restore for the entries ticked in a list, in the shapes the user approved on 2 November 2026. Each acts on ids, so it changes exactly what was ticked.

`GET /api/types/:type/entries/ids` takes `where`, `order` and `archived=true` as `GET /api/types/:type/entries` does, checks them the same way, and replies the ids of every entry they find, in that order and then by id, as the list's pages have them. It isn't paged. Past 10,000 it replies 400, "More than 10,000 entries match. Narrow the search or filter to 10,000 or fewer."

```json
{ "data": ["0192f0c4-…", "0192f0c5-…"] }
```

`POST /api/types/:type/entries/archive` and `POST /api/types/:type/entries/restore` take `{ "ids": ["0192f0c4-…", …] }`, 1 to 100 of the type's entries, each sent once, whatever its case, as Postgres ignores a UUID's case, or reply 400, with 404 for an unknown type and 409 for a singleton. Each request is one transaction. Archive archives each entry with its descendants that aren't archived, as `POST /api/entries/:id/archive` does, all stamped with one time, so restoring one of them brings back just what was archived along with it, and takes them off the live site. Restore restores each with the descendants archived along with it, as drafts, as `POST /api/entries/:id/restore` does, parents before their pages, at any depth, so a page sent with its parent comes back after it. Both reply 200 with a result for each id, in the order sent and as it was sent, as bulk saves do: 200 with the entry as it is now in `data`, one already archived, or already restored, included, 404 for an id that isn't an entry of the type, and for Restore, 409 for a page whose parent stays archived.

```json
{
  "data": [
    { "id": "0192f0c4-…", "status": 200, "data": { "id": "0192f0c4-…", "archivedAt": "2026-11-02T20:14:03.000Z" } },
    { "id": "0192f0c5-…", "status": 404, "message": "There's no entry of this type with this id." },
    { "id": "0192f0c6-…", "status": 409, "message": "Its parent is archived. Restore the parent first." }
  ]
}
```

Each entry writes its events, as the single routes do, so an automation on `entry.archived`, `entry.unpublished` or `entry.restored` runs for every one.

`POST /api/types/:type/entries/used-by` takes `{ "ids": [...] }` the same way, 1 to 10,000 of them, for bulk Archive to warn of the links it breaks. It replies how many of those entries that aren't archived yet, or of the pages under them, other entries link to, counting each entry once. Links from among them or from pages under them, which leave the site with them, and from archived entries don't count, so an entry linked from nowhere else isn't counted.

```json
{ "data": { "count": 12 } }
```
