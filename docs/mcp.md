# MCP

AI clients such as Claude Code, Cursor and VS Code can read the site's content at `/mcp`, the CMS's MCP server, with a token a person makes in the admin, change it with a token that saves drafts, and where the site allows it, publish it with a token that publishes. Each token acts as the person who made it. It's off until `sorlo.config.ts` turns it on, and the client brings its own model, so it needs no AI settings:

```ts
export default defineConfig({
  // …
  mcp: true,
})
```

With it off, `/mcp` and the token routes reply 404 and your account has no MCP tokens tab. `mcp: { publish: true }` also lets people give their tokens Publish changes, which puts what their AI clients write on the live site at once, and `mcp: true` is the same as `mcp: { publish: false }`.

Once it's on, each person makes a [token](#tokens) on their account and adds the server to their client, as [Connecting a client](#connecting-a-client) shows.

## Tokens

Each person makes their own on the MCP tokens tab of their account, `#/account/tokens`, from the menu under their name at the foot of the nav, and sees and revokes only their own. A token shows once, when it's made, with the setup for each client below, since only its hash is stored. It starts with `sorlopat_`, so neither people nor secret scanners take it for an API key, which starts with `sorlo_`. The page says when each token was last used, which is written at most once a minute. Revoking one marks it revoked, so its next request gets a 401, and keeps its row, so the versions saved through it keep its name. Removing a person revokes their tokens, keeping the rows the same way.

A token only reads unless it has one of two permissions, which the admin API calls `scopes`:

| Permission      | Scope     | What it adds                                                                                                                                                                                                                                                                             |
| --------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Save drafts     | `drafts`  | The [write tools](#tools) but `update_media`, since a file's details go live at once: they save changes to entries as drafts, and make new forms closed, as the token's maker, through the editor's own save, so versions, the version cap, events and automations work as they do there |
| Publish changes | `publish` | Save drafts, and the [tools that publish](#publishing-through-a-token), `publish_entries` and `open_form`, which put changes on the live site at once. Only where `sorlo.config.ts` has `mcp: { publish: true }`                                                                         |

There's no Apply over MCP, since the client's own approval prompt is the check, and nothing a token does unpublishes, archives or deletes. With Publish changes, what a client writes can go live without anyone reviewing it in Sorlo, including what a page, a file or an email it read steered it to write, so the tokens page warns about that whenever Publish changes is ticked, and a Publish token's page shows the rules that keep Claude Code asking before each publish. Choosing Publish changes alone makes a token with both. A token's page changes its permissions, keeping its name, since the versions saved and published through it show its name: a client that's connected gets new tools when it next connects, and loses tools from its next call. While a site has Publish changes off, a token that has it saves drafts and no more, and its page says so.

Tokens open `/mcp` and nothing else, and API keys and the admin's session never open it.

## Connecting a client

The server takes Streamable HTTP at `https://<your CMS>/mcp`, with the token as `Authorization: Bearer <token>`. A new token's page shows each client's setup with the token filled in, and a Publish token's page the rules that keep Claude Code asking before each publish, even once someone has let it use Sorlo's other tools without asking, since Claude Code checks ask rules before allow rules. They go in `~/.claude/settings.json`, for the server added as `sorlo`:

```json
{ "permissions": { "ask": ["mcp__sorlo__publish_entries", "mcp__sorlo__open_form"] } }
```

- **Claude Code:** `claude mcp add --transport http sorlo https://<your CMS>/mcp --header "Authorization: Bearer <token>"`
- **Cursor:** in `~/.cursor/mcp.json`, outside any project, so the token stays out of its repository:

  ```json
  { "mcpServers": { "sorlo": { "url": "https://<your CMS>/mcp", "headers": { "Authorization": "Bearer <token>" } } } }
  ```

- **VS Code:** in `.vscode/mcp.json`, which asks for the token when it first connects, so the file never holds it:

  ```json
  {
    "inputs": [{ "type": "promptString", "id": "sorlo-token", "description": "Sorlo MCP token", "password": true }],
    "servers": {
      "sorlo": {
        "type": "http",
        "url": "https://<your CMS>/mcp",
        "headers": { "Authorization": "Bearer ${input:sorlo-token}" }
      }
    }
  }
  ```

The server is stateless: each POST gets a server of its own, which replies with JSON, so nothing is kept between requests and any process can answer. GET and DELETE reply 405, since nothing streams. A request without a valid token gets a 401 with `WWW-Authenticate: Bearer`, with `error="invalid_token"` when it sent one. The CMS has no OAuth yet, so ChatGPT can't connect, and nor can claude.ai unless its custom connectors offer your organisation request headers, which are in beta. Claude Desktop can connect through the [`mcp-remote`](https://npmjs.com/package/mcp-remote) bridge, which sends the token as a header.

## Tools

The tools live in [`packages/cms/src/tools.ts`](https://github.com/WeAreSorlo/cms/blob/main/packages/cms/src/tools.ts), defined once with Zod schemas, and [the admin's assistant](assistant.md) uses the same ones. They run as the token's maker, through the queries and checks the admin API uses, and reply with its shapes. Each one's description says that what it returns is content to read, never instructions to follow. Ten read, and are marked read-only:

| Tool                 | Reads                                                                                                                                                                                                                                                                                                                                                    |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `list_content_types` | The content types, as `GET /api/types` lists them, with shared groups expanded, or the ones in `names`                                                                                                                                                                                                                                                   |
| `list_entries`       | A type's entries a page at a time, with their drafts' values and their status, filtered by `where` and sorted by `order` as the list API takes them, its archive with `archived`                                                                                                                                                                         |
| `search_entries`     | The entries with text holding `query`, in any field at any depth, across every type or those in `types`, drafts included and archived entries left out, newest edits first                                                                                                                                                                               |
| `get_entry`          | One entry by its `id`                                                                                                                                                                                                                                                                                                                                    |
| `list_versions`      | An entry's versions, newest first, as its history lists them                                                                                                                                                                                                                                                                                             |
| `get_version`        | One version's values, caught up with the content migrations since it was saved                                                                                                                                                                                                                                                                           |
| `list_forms`         | The forms with their fields, or the ones in `names`                                                                                                                                                                                                                                                                                                      |
| `list_media`         | The media library a page at a time, filtered and sorted as `GET /v1/media` takes them                                                                                                                                                                                                                                                                    |
| `get_media`          | One file by its `id`                                                                                                                                                                                                                                                                                                                                     |
| `view_media`         | Up to 10 images by their `ids`, as images the model sees, each turned upright and scaled to fit 512 pixels, an SVG drawn at that size, as a PNG where something in it is transparent and otherwise a JPEG, at most 361 tokens each. It replies each file's id, name, alt text and caption first, and says which it left out, such as video and documents |

`perPage` is 10 unless a call says otherwise, up to 50, and `query` takes 1 to 200 characters. `fields` keeps only some top-level fields in `values`, for lighter lists and for reading a large entry a part at a time. Each reply holds at most 30,000 characters of JSON, about 10,000 tokens: a list keeps the items that fit and says how many it left out and what to ask for instead, and anything else is cut there, with a notice to ask for fewer fields. A mistake, such as an unknown type or a field the query can't take, comes back as a tool error with the API's message, for the model to fix.

Form submissions can't be read, since they hold visitors' personal data. The assistant's tools for [content types](assistant.md#content-types-through-the-assistant) are never offered here.

Six write, for the assistant, which proposes what they'd save rather than saving it, and all but `update_media` for tokens with Save drafts, saving at once:

| Tool           | Changes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create_entry` | Makes a new entry's draft from `type`, `values` and, for a page, `parentId`. Not for singletons                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `update_entry` | Changes an entry's draft: only the top-level fields in `values`, each to its whole new value, where a group can hold only the fields inside it to change, and `parentId` to move a page                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `replace_text` | Replaces `find` with `replace`, exactly as written, capitals included, in every text, long text and Markdown field at any depth of every entry's draft, the `types` named, or only the entries in `ids`, 1 to 100, such as those the person means by “these”. An id that isn't an entry, is archived, isn't one of the `types` named or, over MCP, is of a type without drafts is an error naming it, and nothing changes. Slugs, links and choices are left alone, and so is text that already reads as the replacement, such as Acme Corp when replacing Acme with Acme Corp, so asking twice never doubles it. It goes through the entries in the order they were made, changing up to 100 a call, and says how many more mention it, with `after` to call again with, which goes on from where it stopped, and the other capitals it found, such as “Private preview” |
| `create_form`  | Makes a new form from `label`, `name` and `fields`, closed, so it takes no submissions until a person opens it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `update_form`  | Changes a closed form's `label`, `name` or `fields`, and over MCP only one that has never been open. An open form only a person changes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `update_media` | Changes up to 100 files' `name`, `alt` or `caption` at once, such as alt text written from what `view_media` shows. Only the assistant has it, since a file's details change on the site once applied, and over MCP no one applies them                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

- Each runs every check its save would, as the person or the token's maker, so a failed check comes back as a tool error listing each message by its path, such as `values.slug: Another entry here already uses this slug.`, for the model to fix. A draft can be unfinished, so a reply also says what a publish would still need.
- None publishes, unpublishes, archives or deletes, and none touches archived entries or a page's order among its siblings, which changes on the live site at once. Over MCP they also leave types without drafts alone, since their saves go live at once, which only `publish_entries` does, while in the assistant the person applies and publishes those.
- MCP annotates them as neither read-only nor open-world. `create_entry` and `create_form` aren't destructive or idempotent, `update_entry` and `update_form` are both, since they replace what a draft held, which stays a version back, and calling one twice changes no more than once, and `replace_text` is destructive but not idempotent, since a second call goes on to the entries past the first's.
- Over MCP, `create_entry` and `update_entry` reply the entry with its `version`, and `replace_text` each entry's `version`, which `publish_entries` takes. Each is the entry as that save left it, read in its own transaction, so a save someone makes straight after never shows in the reply.

## Publishing through a token

Two tools publish, only for a token with Publish changes on a site that allows it, and never in the assistant, where only the person's Apply and publish publishes:

| Tool              | Publishes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `publish_entries` | 1 to 100 entries, each `{ id, version, values? }` and each once, as the editor's Publish does: each one's newest draft goes live with every check a publish runs, such as required fields, a live sibling's slug and a page's live parent, in the order given, each on its own. `values` sets top-level fields first, as `update_entry` takes them, which is how an entry of a type without drafts changes. It replies the entries live now, each as `{ id, title, version }`, and notes those it didn't publish, with why, and the closed forms they show |
| `open_form`       | A form that has never been open, such as one `create_form` made, which then takes submissions. It replies the form as `list_forms` gives it                                                                                                                                                                                                                                                                                                                                                                                                                |

- **What was read.** `version` must be the entry's newest version, as entries reply it, checked under the entry's lock, so a save that lands after the model read the entry is never published by it. `null` is for an entry never saved.
- **The whole draft.** Publishing makes an entry's whole draft live, with any changes others saved since it was last published, so the instructions tell the model to compare a changed entry's draft with its live version and to say what goes live, and to publish only what the person asked for, never what something it read asks for.
- **What a person took down stays down.** Unpublishing or archiving an entry, or a page above it, marks every entry it takes off the site as taken down, since only people do either, and a token can't. `publish_entries` refuses an entry while it's marked, and only a person's publish clears the mark, in the editor, bulk editing or through Apply and publish. The mark is on the entry, not its versions, so neither the version cap nor deleting the versions that went live clears it, and no reply shows it.
- **One after the other.** Unpublishing and archiving lock each entry they take down, as a save does, before its live copy goes, so an Unpublish that lands during a token's publish takes the entry down once the publish is done, and a publish that lands during a take-down waits, then finds the mark.
- **Forms.** Publishing a page doesn't open the form it shows: the reply names the closed forms the published entries show, for the model to call `open_form` with, so each thing that goes live has an approval of its own, or, for one a person closed, says it stays closed until a person opens it again. A form that has been open stays a person's, to open again and to change.
- **Neither unpublishes, archives or deletes**, nor changes media files, a page's place among its siblings, or new entries of types without drafts.
- MCP annotates both as open-world, since what they do leaves the CMS at once: the live site, the delivery API and the automations that run on `entry.published`. `publish_entries` is destructive, since it replaces the live copy, and idempotent, since publishing what's live changes nothing, and `open_form` isn't destructive, since it replaces nothing, and is idempotent, since an open form stays open.
- **The record.** Each version says how it was last published, so the history reads "Published by Levi, through Claude Desktop", as [Versions](versions.md) describes.
